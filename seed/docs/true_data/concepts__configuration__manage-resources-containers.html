Resource Management for Pods and Containers

Source: adapted from kubernetes.io — Resource Management for Pods and Containers.

Requests vs. limits

A request is what the scheduler uses to decide which node can fit the Pod — the kubelet reserves at least that much for the container. A limit is the ceiling the kubelet (and ultimately the kernel) enforces: the container is not allowed to use more.

How each resource is enforced

CPU limits are enforced by throttling — the kernel restricts CPU access once a container approaches its limit; a container simply cannot use more CPU than its limit allows.

Memory limits are enforced reactively, by the kernel's out-of-memory killer. A container can briefly use more memory than its limit; if the kernel detects memory pressure, it may terminate ("OOM kill") the container. This is why a container can run fine for a while and then suddenly get OOMKilled once memory pressure hits.

Quality of Service (QoS) classes

Kubernetes assigns every Pod a QoS class based on its requests/limits, and uses it to decide eviction order under node memory pressure:

  • Guaranteed — every container has both a memory and CPU limit, and the request equals the limit for each. Evicted last.
  • Burstable — at least one container has a request, but the Pod doesn't qualify for Guaranteed. Evicted after BestEffort, before Guaranteed.
  • BestEffort — no requests or limits set at all. Evicted first under memory pressure.

A critical workload that needs its compute reserved and wants to survive node pressure should be given matching requests and limits — i.e. the Guaranteed class.
