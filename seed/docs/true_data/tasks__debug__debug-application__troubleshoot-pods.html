Troubleshoot Running Pods

Source: adapted from kubernetes.io — Debug Running Pods and Assign Memory Resources to Containers and Pods.

Start with kubectl describe and kubectl logs

When a Pod is misbehaving, start with kubectl describe pod <name>. The output shows the container state (Waiting, Running, or Terminated), the ready status, the restart count, and a list of recent events with timestamps and messages. Use kubectl logs <pod> (add --previous to see the logs of the last crashed instance) to see what the application itself printed before it died.

CrashLoopBackOff

If a container is exiting and being restarted very frequently, Kubernetes increases the delay before the next restart attempt exponentially — starting at 100ms and capping at 5 minutes. This exponential backoff is what shows up as the CrashLoopBackOff status: the container isn't dead, it's crashing, restarting, and being made to wait longer between each attempt. Check kubectl logs --previous for why the process is exiting, and kubectl describe pod's events section for anything about failing probes, missing config, or an unrecoverable startup error.

OOMKilled

A container is not allowed to use more memory than its configured limit. If a container tries to allocate more memory than its limit, the kernel may terminate it. This shows up in kubectl describe pod as:

lastState:
   terminated:
     exitCode: 137
     reason: OOMKilled

Exit code 137 plus reason: OOMKilled means the container ran out of memory and was killed by the kernel. If the container's restart policy allows it, the kubelet restarts it — and it can be OOMKilled again if the underlying memory usage doesn't change. The fix is to raise the container's memory limit, or reduce what the application actually needs to hold in memory.

ErrImagePull / ImagePullBackOff

This means the kubelet could not pull the container image. Common causes: a misspelled image name or tag, a tag that doesn't exist, or missing credentials for a private registry. Kubernetes pulls images using the name you give it in spec.containers[].image — always include the registry hostname for a private registry (e.g. my-registry.example/my-image:1.2) and a specific tag rather than relying on :latest. For a private registry, attach credentials to the Pod with imagePullSecrets, or configure the node to authenticate to the registry directly. kubectl describe pod's events section shows the exact pull error returned by the registry, which usually tells you whether it's a naming problem or an auth problem.
