Pod Lifecycle

Source: adapted from kubernetes.io — Pod Lifecycle.

Pod phases

A Pod's status.phase is a simple, high-level summary of where it is in its lifecycle — not a full state machine.

  • Pending — accepted by the cluster, but one or more containers aren't set up and ready yet (includes time spent waiting to be scheduled and time spent pulling images).
  • Running — bound to a node, all containers created, and at least one container is running, starting, or restarting.
  • Succeeded — all containers terminated successfully and will not restart.
  • Failed — all containers terminated and at least one exited with a failure.
  • Unknown — the Pod's state couldn't be obtained, usually a communication error with the node.

Container states

Within a Pod, each container is independently in one of three states:

  • Waiting — the container is doing setup work, such as pulling its image; kubectl describe pod shows a Reason for why.
  • Running — executing without issues.
  • Terminated — started, then either completed or failed; kubectl describe pod shows a reason, exit code, and start/finish time.

Restart policy

restartPolicy applies to every container in the Pod. Values: Always (default — restart on exit), OnFailure (restart only on non-zero exit), Never. If containers keep exiting and restarting very frequently, the delay before the next restart increases exponentially — 100ms up to a 5-minute cap — which is what produces the CrashLoopBackOff status.

Probes

The kubelet runs three kinds of probes: startup (delays the other two probes until the app has finished starting), liveness (restarts the container if it's stuck/deadlocked), and readiness (controls whether the Pod receives traffic — a Pod is only "ready" when all its containers pass their readiness probe, and Services stop routing to it otherwise).

Termination

By default a Pod gets a 30-second grace period on delete: a TERM signal is sent first, and if the process hasn't exited by the end of the grace period, a KILL signal follows.
